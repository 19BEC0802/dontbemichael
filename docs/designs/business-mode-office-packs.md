## Problem Statement

Dont Be Michael (which grew out of Munder Difflin) runs an office of AI agents on the owner's machine. Today it is a developer tool. Onboarding asks for a harness folder, a CLI engine and model ID, and git repos. The Add Agent form edits raw spawn commands, working directories and worktrees. The workspace shows terminals, a Monaco IDE and git panels. A non-technical owner can't get past setup, and the "non-technical" persona only changes the wording (`OnboardingWizard.tsx`, `descPlain` copy keys).

The app keeps Claude Code as the hidden engine and keeps the hive (mailboxes, router, ledger, breaker, memory, schedules). It replaces everything the owner sees with a business-first flow: pick a business type, pick a starter team of specialized agents, connect the accounts those agents need inside the product, and run the office from the desktop app.

Business model: the app stays open source (MIT). A separate Pro plan (support, training, consulting, dedicated support) is sold on the website and is not built into the app.

## Demand Evidence

- The founder runs an "AI for small business" program for the Greater Austin Asian Chamber of Commerce: "there is a genuine demand by small businesses to leverage AI to do their work as most of them are single person run businesses."
- This is a real distribution channel: a room of owners the founder already reaches.
- **Gap:** no individual member has been named yet (asked twice). The evidence so far is program-level interest, not one owner's behavior. The Assignment closes this gap.

## Status Quo

In the founder's words: "some are pure chatgpt people or worse using chatgpt like google, some know a bit of tools to use to do some part of their business, some knows claude code but not technical enough to run end to end automation like this project can do."

- **ChatGPT-as-search users:** too far from this product for v1 (they would need a Claude plan, an install, and trust in agents all at once).
- **Partial tool users:** stitch together separate apps by hand.
- **Claude Code-aware but stuck:** already pay for the engine and have hit the automation wall. This is the wedge.

## Target User & Narrowest Wedge

- **User:** a solo restaurant or food owner in the chamber program who already uses Claude or Claude Code but can't wire end-to-end automation.
- **First job that broke:** social posts and daily specials. Low risk, visible every day, easy to approve.
- **Wedge:** the **Restaurant & Food Office Pack**. Michael (orchestrator, always on) plus a recommended cast the owner picks from:
  - Oscar (finance, part of every pack);
  - Pam (admin, email triage);
  - Kelly (customer care, inquiries and complaints);
  - Ryan (marketing, promotions and specials);
  - Creed (quality, checklists).
  - Each pick opens its connector setup.

## Constraints

- **Engine:** the Claude Code CLI; owners are expected to be on Claude Max. The hive drives interactive CLI sessions. `src/main/hiddenClaude.ts` deliberately avoids `claude -p` so usage draws on plan quota rather than the separate Agent SDK credit pool (per its code comment). Plan limits therefore apply to the whole office.
- **Delivery:** every provider in `src/shared/agentProvider.ts` uses `inboxDelivery: 'terminal'`. The harness types each inbound message into the agent's live CLI session. Business mode hides terminals but still depends on this path. See Open Question 5.
- **Always-on host:** agents run only while the desktop app is open and the machine is awake.
- **No OAuth support today:** `src/shared/integrations.ts:262-264` leaves Gmail, Calendar and Salesforce out because there is no `oauth2` auth type, and OAuth refresh was a v1 non-goal for upstream. Every restaurant connector (email, Google Business Profile, Instagram/Facebook, QuickBooks) needs OAuth, so this design adds an OAuth broker (Recommended Approach §4). This is the largest new build.
- **Existing secret handling to build on:**
  - Integration secrets are encrypted at rest with Electron `safeStorage` (`src/main/integrations.ts:111-132`), which refuses to store a secret when OS encryption is unavailable.
  - The loopback broker (`src/main/integrationBroker.ts`) injects the credential upstream, so an agent never sees it.
- **Per-agent enforcement exists:**
  - `control.ts:107` `toolDecision` denies gated tools per agent through the PreToolUse hook.
  - Per-session settings files carry `mcpServers`, sandbox and hooks and never write `~/.claude` (`hive.ts:1146`).
  - The only global writes are the skip-permission-prompt flags (`config.ts:786-858`).
- **Windows has no sandbox:** the OS sandbox block in `hookSettings` runs without isolation on Windows.
- **Licensing:** code is MIT, and the LimeZu pixel art needs credit (`LICENSE-ASSETS`).
- **Upstream:** keep bug fixes flowing from Munder Difflin where practical.

## Premises

Agreed after the founder revised #2 through #6, then refined at the wireframe review:

1. **Wedge user:** chamber members who already use Claude or Claude Code but can't run end-to-end automation.
2. **Starter team:** business type leads to Michael plus a recommended cast.
   - The owner picks any subset as a starter template, and each pick opens that agent's default config and connector setup (picking Pam asks to connect email).
   - **Oscar (finance) is recommended in every pack, because every business needs finance.**
3. **Desktop control room:** the owner monitors, approves and rejects in the Mac/Windows app. Agents run autonomously and earn more autonomy as they learn.
4. **Agent Definition v2:** role, what to do, what not to do, and a per-agent tool allowlist (for example, the marketing agent can't read email). The owner refines each agent's defaults. **"Won't" rules are owner-editable starting defaults, not fixed limits: an agent can do anything the owner turns on.**
5. **Connectors in the product:** connectors are configured in the product UI, reusing the engine's connector mechanism (MCP) underneath. The owner never touches Claude Code setup.
6. **Plan and schedule:** owners are expected to be on Claude Max. The product lets the owner choose the model and set an office schedule (for example, pause during lunch). Kept after an outside challenge.

## Approaches Considered

### Approach A: Business Mode in the existing app (chosen)

- Keeps the hive untouched.
- Adds the business onboarding, the Agent Definition v2 schema, the OAuth broker, a connector center, an approvals inbox and an office schedule.
- Hides developer surfaces in business mode.
- Effort L (human ~2 months / CC ~2-3 weeks).
- **Risk medium-high.** The drivers:
  - the OAuth broker, which is net-new security-sensitive code;
  - third-party app approvals (Meta, Google), whose timelines we don't control;
  - developer UI leaking through a missed mode check.
- The build order below puts the connector-free work first, so the pilot isn't blocked on those approvals.

### Approach B: Business Edition on an extracted hive core

- Splits the code into `hive-core` with an Engine adapter, plus a new owner app.
- Cleanest long term. Effort XL (human ~5 months / CC ~6-8 weeks).
- **Not chosen now:** months before any chamber owner uses it, and extracting from `hive.ts` (3.5k lines mixing CLI flags, git and routing) is risky. A's schema, broker and pack format are what B would extract later.

### Approach C: Office Packs + chamber concierge

- Portable pack files authored from real member setups, with a thin importer app.
- Effort M.
- **Not chosen alone:** too thin for owners who download on their own. **Its pack format is adopted as A's template layer.**

## Recommended Approach

Approach A, with Office Packs as the template format.

### 1. Office Pack format (`dontbemichael/office-pack@1`)

A portable JSON file that extends the existing `hire@1` manifest validator (`src/shared/hire.ts`) rather than replacing it.

- **Core pack:** `resources/packs/core.json` holds the agents every business needs.
  - v1 contains only Oscar (finance).
  - Every business pack inherits the core agents. A pack may tune a core agent's `does` / `wontDo` / `tools` for its industry (restaurant Oscar watches food cost and supplier invoices) but can't remove it. The validator enforces this, so community packs can't leave out finance.
  - The owner can still leave Oscar unpicked.
- **Import:** through the existing file and deep-link path (`index.ts:2170-2240`). An import only pre-fills the form; the owner still confirms.
- **Distribution:** bundled packs ship in `resources/packs/`. Community packs are contributed by PR.
- **v1 packs:** Restaurant & Food only, plus a generic "Something Else" pack Michael fills in by asking questions. Retail, Pro Services, Salon and Home Services follow once the restaurant pack survives real owners.

Shape, for orientation only (the implementation plan fixes names and validation):

```ts
interface OfficePack {
  spec: 'dontbemichael/office-pack@1';
  businessType: string;            // 'restaurant-food'; 'core' for the core pack
  displayName: string;             // 'Restaurant & Food'
  tagline: string;                 // 'cafe, catering, food truck'
  extends?: 'core';                // every business pack; the core pack omits it
  agents: AgentDefinitionV2[];     // business roles, plus overrides of core agents by id
  defaultPicks: string[];          // agent ids pre-checked on the team screen (core agents included)
  officeHours: {
    days: ('mon'|'tue'|'wed'|'thu'|'fri'|'sat'|'sun')[];
    work: { start: string; end: string };        // '09:00'..'22:00', owner's local time
    pauses: { start: string; end: string; label: string }[];
  };
  starterMissions?: { agentId: string; title: string; schedule: string }[];
}
// Michael is always on and never listed in a pack.
```

### 2. Agent Definition v2

```ts
type ToolLevel = 'off' | 'ask' | 'auto';

interface AgentDefinitionV2 {
  id: string;                      // 'pam'
  character: OfficeCharacterName;  // cast.ts
  role: string;                    // 'Admin'
  summary: string;                 // one plain sentence shown on the team card
  does: string[];                  // plain-language starting rules, owner-editable
  wontDo: string[];                // starting defaults, owner-editable; not shown on team cards
  connectors: { kind: string; required: boolean }[];   // 'email', 'google-business', 'meta', 'quickbooks'
  tools: { capability: string; level: ToolLevel }[];   // 'email.read', 'email.send', 'social.post'
  modelTier?: 'best' | 'fast';     // mapped to a concrete model id in main, never shown
  tokenCap?: number;
}
```

Enforcement follows whatever the owner has set. Layers, strongest first:

1. **The agent is never given an MCP server it isn't allowed to use.** Per-session `mcpServers` includes only its connectors, and within a connector only the capabilities not set to `off`.
2. **`ask`-level capabilities route through `control.ts` gating** into the approvals queue.
3. **`off`-level tools are gated** (and passed as `--disallowedTools` where applicable).
4. **`does` / `wontDo` compile into the appended system prompt** as reinforcement only, never as the enforcement layer.

If the owner turns something on (for example Pam sending email on her own), every layer updates to match. Nothing is hard-coded as off.

### 3. Business onboarding (replaces the dev wizard steps when the audience is business)

1. **Business name, city and business type.** The Claude install and sign-in check runs silently.
2. **Starter team picker.**
   - Michael is always on.
   - Core agents (Oscar) and recommended agents come pre-checked.
   - "Needs" chips show each pick's setup cost.
   - No "won't" tags on these cards.
   - Office hours are set here.
3. **Per-agent setup, in pick order:**
   - connect account (OAuth broker);
   - edit the job in plain words ("does" and "won't" are starting rules);
   - set tool levels.
4. **Land on the floor** with the approvals inbox open.

- Engine is fixed to Claude Code, and the model is chosen by friendly tier (`best` / `fast`) in Settings.
- The harness folder is created silently.

**Failure and empty paths.** Each has one plain sentence and one next action:

| Situation | What the owner sees | Next action |
|---|---|---|
| Claude not installed | "Claude isn't on this computer yet." | [Install Claude] runs the existing `cliInstall.ts` flow with no visible terminal |
| Claude not signed in | "Sign in to Claude. A Max plan is recommended." | [Sign in] opens login in a hidden session. The app has no verified way to read the plan tier, so it recommends Max rather than checking it; limits surface through §7 |
| OAuth window closed or cancelled | "Google sign-in was closed before it finished." | [Try again] |
| Wrong account (e.g. personal Gmail where the pack expects the business inbox) | Shows the signed-in address | [Use this account] / [Switch account] |
| Provider denies a permission scope | "Pam needs permission to read email to sort it." | [Try again]; otherwise the agent stays paused |
| Owner clicks "Skip for now" | Agent saved as **paused · waiting for account** | Card on the floor: [Connect] |
| Token later expires or is revoked | That agent pauses; approvals inbox card "Reconnect Google" | [Reconnect]; the other agents keep working |
| "Something Else" business type | Michael asks 3 plain questions (what you sell, who contacts you, what slips) | Builds a team from the core pack plus the generic pack; never a dead end |
| Owner wants roles from another pack later (e.g. a restaurant adds a retail counter) | Settings → "Hire from another pack" | Adds agents alongside the current team; existing agents, memory and connectors stay; the wizard is not re-run |

- Wireframe (revision 2): `docs/designs/business-mode-office-packs-wireframe.png`, with its source at `docs/designs/business-mode-office-packs-wireframe.html`. It uses the real `DESIGN.md` tokens; portraits are placeholders in each character's shirt color.

### 4. Connector Center + OAuth broker

A main-process OAuth 2.0 broker:

- System browser with a loopback redirect and PKCE (the sign-in pattern for apps that can't keep a secret).
- Refresh tokens stored through the existing secret store (encrypted at rest with Electron `safeStorage`).
- **Access tokens refreshed inside the loopback broker (`integrationBroker.ts`) before it injects them upstream**, so agents keep never seeing a credential.
- Connectors exposed to agents only through per-session MCP servers or the broker proxy.

**v1 provider order is decided by the Assignment results.** The expected shortlist is Google (Gmail, Business Profile), Meta (Instagram/Facebook), Microsoft 365, and QuickBooks for Oscar. An "Other email" IMAP path is the fallback.

### 5. Business shell

In business mode, hide the terminal panes, IDE, git panels, worktrees, CI/GitHub view, skills catalog, raw spawn/flags fields, the Prerequisites developer list, and model IDs.

Keep:

- **Floor:** the office floor, as the ambient view.
- **Agent cards:** each card shows the agent's job in plain words.
- **Approvals inbox:** approve, reject, or edit and approve.
- **Activity feed:** written in plain language.
- **Office schedule.**
- **Connector Center.**

Leak protection: a test renders business mode and fails on any developer term (`terminal`, `worktree`, `git`, `repo`, `CLI`, model IDs).

### 6. Office schedule

Work window plus pause windows, reusing `weeklySchedule.ts` for day-of-week rules. A pause maps to the existing `control.ts` pause for every agent and resumes at the window end. Work that arrives during a pause (e.g. an inbound email) is queued, not dropped. The manual "Closing time" (`closingTime.ts`) stays as the owner's big red button.

### 7. Plan limits

When the Claude plan's usage limit is reached, every agent on that plan stops getting responses until the window resets.

- **Office-wide event:** the limit is treated as an office-wide event, not as an agent error, and must never trip the circuit breaker as a "loop".
- **Detection:** how the app reliably detects the limit is unverified (Open Question 10). Spike it before building this section.
- **What the owner sees:** the floor shows "Office on break until 3:10 pm (Claude plan limit)". Michael holds new work in the queue, and a notification fires once, not once per agent.
- **Resume:** agents resume automatically at the reset time.
- **Settings:** a plain usage meter, built on the existing usage and cost tracking in `src/main/usage.ts` and `costLifetime.ts`, shows how close the office came to its limit this week. The owner can move a busy agent to the `fast` model tier.

## Engineering Review Decisions

From /plan-eng-review on 2026-09-15, scope: all three phases. Each decision was approved individually.

### Architecture

**1. Closing the window must not silently stop the office** (P1, confidence 9/10)

- **Finding:**
  - On Windows, closing the last window runs `teardownAndQuit()` (`src/main/index.ts:5374-5380`), which kills every agent.
  - On macOS, messages reach agents through a 4-second timer inside the window (`src/renderer/src/hooks/useHive.ts:690-692`), and the main-process fallback skips Michael (`index.ts:5146`).
  - Open Question 5 is also wrong: the Stop hook never drains the inbox (`src/main/hooks.ts:261-264`).
- **Decision:** closing the window asks the owner to choose:
  1. **Minimize:** hide to a tray icon and keep the office running.
  2. **Close all agents gracefully:** run the Closing Time shutdown (`closingTime.ts`), wait a bounded time, then quit.
  3. **Force kill all:** immediate `teardownAndQuit()`.

  Built on the existing `app:closeRequested` flow (`index.ts:5361`), so the red close button and Cmd-Q / dock-quit show the same dialog.
- **Required for Minimize to work:**
  - The window is hidden, not destroyed, so renderer timers keep running (`backgroundThrottling: false` is already set at `index.ts:2310`).
  - Windows no longer tears down on window close.
  - The main-process wake fallback includes Michael.
- **Tests:**
  - win32 window close does not tear down while Minimize is chosen.
  - A graceful close times out into a kill.
  - The main wake fallback delivers to Michael with no renderer.

**2. Capability limits are enforced by the broker, the only component holding credentials** (P1, confidence 9/10)

- **Finding:** §2 enforcement layer 1 relies on MCP server omission plus tool-name gating. But agents reach integrations with plain HTTP from Bash, using a broker token in their environment:
  - the token covers every enabled integration (`src/main/index.ts:4735-4737`);
  - the hook matches exact tool names, so it only ever sees `Bash` (`src/main/control.ts:111`);
  - Claude Code's docs say Bash rules are "not a security boundary around the program" (permissions.md:247).
- **Failure scenario:** Pam's Send is Off, yet `curl` to the broker's Gmail send endpoint still sends the email.
- **Decision:**
  - **Per-agent grants:** an agent's broker token covers only that agent's connectors.
  - **Capability map per connector:** each request's method and path pattern maps to a capability (e.g. Gmail send → `email.send`). The broker checks it against the agent's current `off | ask | auto` level on every request. **Unmapped endpoints are denied by default.**
  - **Live levels:** the broker reads levels from the persisted Agent Definition, so a change applies without respawning the agent.
  - **OAuth scopes follow levels:** a scope is requested only when a capability that needs it is above Off. Raising a level triggers incremental authorization.
  - **Agent-facing tools:** agents use connectors through thin MCP tools that call the broker. Tool-name gating in the hook stays as a second layer.
  - **§2 enforcement order becomes:**
    1. broker capability check;
    2. per-session MCP servers only for the agent's connectors;
    3. PreToolUse gating;
    4. prompt reinforcement.
- **Tests:**
  - capability map matching, including unmapped-endpoint default deny;
  - grant scoping (Ryan's token rejected on Gmail);
  - a level change applies to the next request without respawn;
  - an incremental scope request fires when Send moves above Off.

**3. "Ask me" uses a durable approvals queue; the broker runs the approved request** (P1, confidence 9/10)

- **Finding:** §2 sends `ask`-level calls "into the approvals queue", but no queue exists:
  - `src/main/hooks.ts:272-273` leaves approval to Claude's native prompt.
  - Michael's prompt says "there is NO separate approval queue" (`src/main/hive.ts:1487`).
  - `control:approvalRequest` (`hooks.ts:381`) has no listener in the renderer.
  - A call can't be held while the owner is busy: the hook shim exits after 5 s (`hive.ts:3001`), and Claude Code's command-hook timeout is 600 s.
- **Decision:**
  - **Record:** each approval is persisted in the hive folder as `approvals/<id>.json` with agent, capability, plain-language summary, exact request payload, created and expires times, status, and owner note.
  - **Connector requests at `ask`:** the broker stores the record and immediately returns "queued as approval #id" to the agent.
  - **Approve:** the broker executes the stored request itself, so there is no agent retry and no payload drift, and it delivers the result to the agent's inbox. **Edit and approve** executes the edited payload.

  - **Breaker:** denials caused by a pending approval don't count toward the error storm.
  - **Reuse:** the ASK ME board's answer-lands-in-inbox pattern. In business mode, Michael's "no approval queue" prompt line is rewritten.
  - **Ryan's draft mode:** an approval item whose approve action is "copy to clipboard and mark posted".
- **Tests:**

  - approve executes the exact stored payload exactly once (double-click safe);
  - edit and approve;
  - reject and expiry inbox messages;
  - dedup;
  - one-time grant is consumed;

**9. Connections are central; agents are authorized to use them** (P1, confidence 8/10)

This supersedes the per-agent MCP parts of Decisions 2 and 4.

- **Finding:** Decisions 2 and 4 assumed each agent received only its own MCP servers, written into that agent's settings file (`hive.ts:1168-1172`). That key is undocumented in Claude Code's MCP docs, and per-agent server sets would mean registering the same third-party system twice whenever two agents share one company account.
- **Decision:**

- **Tests:** an agent with zero authorized connections still boots with its hooks, skills and memory intact.

**21. Polling cadence follows office state** (P2, confidence 9/10)

- **Finding:** the window polls every agent's inbox every 4 s plus four other timers (`useHive.ts:591-952`), and main runs the fleet snapshot every 8 s, the breaker every 30 s, worker wake every 15 s and the router every 1.5 s. Decision 1 keeps the window alive in the tray, background throttling is off (`index.ts:2310`), and `powerSaveBlocker` keeps the machine awake (`index.ts:639-648`). A restaurant closed from 10pm to 9am polls for eleven hours for work that cannot arrive.
- **Decision:**
  - While the office is paused, closed, or on a plan-limit break, the inbox poll and worker wake back off to roughly 60 s, and the router idles unless an outbox actually holds mail.
  - **Keep-awake is released when the office is closed**, so the machine sleeps overnight.
  - Normal cadence resumes at opening, with the staggered restart from Decision 6.
  - The UI states that work arriving during closed hours is picked up within about a minute.
- **Tests:** cadence per office state; keep-awake released and re-acquired at the window edges; a message arriving during closed hours is delivered at the next backed-off tick.

Local `gpt-oss:20b` reviewed the full plan and raised 24 items. Each was checked against the document and the code; **6 survived**, and 14 were rejected as contradicted by the plan (approvals idempotency, plan-limit spike ordering, UX validation, `safeStorage` availability checks, code signing, battery handling, free-versus-pro gating, PKCE details) or already open questions (Windows sandbox, upstream sync).

**22. Approval execution is serialized, and state is re-checked before commit** (P2, confidence 8/10)

- **Finding:** the file layer is already safe — registry, cursor and inbox writes are atomic (`hive.ts:756`, `:1544`), and the task ledger has a merge backstop for competing writers (`taskLedger.ts:53`). What no decision covered is ordering across the new pieces. Two approvals can execute at once against one connection while the lunch pause starts, Michael patches the same card as the ledger's scribe, and a capability-level change lands mid-flight. Every write succeeds; the sequence is undefined.
- **Failure scenario:** an approval still shows as pending for an email that was already sent, so the owner sends it twice.
- **Decision:**
  - All approval execution and card writing flows through **one queue in the approvals module**, with at most **one in-flight execution per connection**.
  - Office state and the agent's capability level are read when execution starts and **re-checked before the result is committed**, so a pause or a revoked level cannot land mid-flight.
  - Card patches go through the existing `patchTaskInLedger` path.
  - Per-connection serialization is also where third-party rate-limit backoff belongs (surviving outside finding 4).
- **Tests:** concurrent approvals on one connection execute in order; a pause starting mid-execution is observed at commit; a level revoked mid-flight stops the commit.

**23. Every owner-side record carries a schema version and upgrades on read** (P2, confidence 8/10)

- **Finding:** this plan puts four new kinds of state on owners' machines — Office Packs, the connections registry, Agent Definition v2 records and approval cards — on top of `config.json`, `registry.json`, `roster.json`, `tasks.json` and `integration-secrets.json`. Owners auto-update, so builds will read each other's files in both directions. The plan names `dontbemichael/office-pack@1` but never says what `@2` does, and the one precedent in the code is unforgiving: the hire validator matches its spec string exactly and rejects anything else (`hire.ts:177-179`).
- **Precedent to follow:** the SQLite side already does this properly — ordered, append-only `PRAGMA user_version` migrations where "migration N runs when user_version < N+1, then bumps it. NEVER edit a shipped migration — only append" (`src/main/db.ts:12-15`, `:32`, `:49`, `:91-93`). The JSON records adopt the same discipline.
- **Decision:**
  - Packs, connection records, agent definitions and approval cards each carry a schema version.
  - The app **upgrades older records in place when it reads them**, through a small function per version step, and writes the upgrade back atomically so a crash mid-upgrade leaves the original intact.
  - A **newer** record on an older build is refused with a plain "update the app to open this" message rather than a parse error.
  - Migrations are append-only and never edited once shipped.
- **Tests:** one test per migration step; a newer-version record produces the update message; an interrupted upgrade leaves the old file readable.

**24. Business mode records a minimum Claude Code version and probes for the features it needs** (P2, confidence 8/10)

- **Finding:** Decision 4 depends on `dontAsk` mode plus compiled allow and deny rules, and Decision 5 depends on the `StopFailure` `rate_limit` matcher and the `quota_auto_resume_*` notifications. Claude Code pins features to versions routinely: the Manual alias needs v2.1.200 or later, strict MCP config needs v2.1.246, and one `StopFailure` matcher needs v2.1.267. Owners install and update Claude on their own schedule. The app today checks presence, not capability, and deliberately avoids version probes because running `--version` per provider "would be a dozen process launches on every panel open" (`index.ts:3592`).
- **Failure scenario:** on an older Claude the permission model silently degrades to whatever that version does, which is the fail-open case Decision 4 exists to remove, and nobody notices until an agent does something the owner set to Off.
- **Decision:**
  - Record a **minimum Claude Code version** for business mode and check it when the office starts, with a plain message and an "Update Claude" action when it is too old.
  - Run a **capability probe** that confirms behavior rather than a number: `dontAsk` denies a tool that is not in the allowlist, and the quota hook fires in a rehearsal. Cache the result per version string so later starts cost nothing.
  - Spikes S2 and S3 produce the expected values for the probe.
  - If a probe fails, offer to **continue with reduced autonomy** (agents need approval for more actions) rather than blocking startup outright.
- **Tests:** version comparison including pre-release strings; the probe result is cached per version; below the floor, the message appears and no business agent spawns with bypass permissions.

**25. One "Needs your attention" strip carries every state the owner must act on** (P2, confidence 8/10)

- **Finding:** failures reach Michael as an inform message (`index.ts:500-512`), and the only thing that reaches the owner today is a breaker notification (`index.ts:1178-1183`). The approval event the app already emits has no listener (`hooks.ts:380-382`). This plan adds six more states an owner must notice: an agent paused waiting for an account, a connection needing reconnection, the office on a plan-limit break, a failed capability probe, a pack that would not load, and a record refused by a version check.
- **Decision:**
  - Phase 1 ships a minimal strip on the floor showing **paused agents** and the **office-on-break** state.
  - Every later decision adds its state to this strip instead of inventing its own alert. The rule: **anything that needs the owner appears here.**
  - It reuses the approvals inbox rendering but stays visually distinct, so the two never read as one list.
- **Tests:** one per state; a state that clears removes its row; the strip and the approvals inbox never show the same item twice.

**26. Main-process integration tests now; a UI driver later** (P2, confidence 9/10)

- **Finding:** seven flows in the coverage map need end-to-end proof, and there is no harness: the suite is `node --test test/*.test.cjs`, there is no Playwright or Cypress config, and exactly one Electron test exists (`test/quit-sweep.electron.test.cjs`). The success criteria ("three owners from install to a first running agent in under 20 minutes") are end-to-end claims.
- **Decision:** approvals, office state, plan limits, packs and connection authorization are driven end to end through the injected modules from Decision 12, inside the existing `node --test` suite that CI now runs. No new framework. A UI-level driver for onboarding clicks and the close dialog stays a TODO until those screens settle.
- **Tests:** five integration flows; the remaining two stay manual until the UI driver exists.

## Design Review Decisions

From /plan-design-review on 2026-09-16. Each decision was approved individually. Initial design rating: 5/10.

### Pass 1 — Information Architecture (4/10)

**27. The owner's floor layout is defined** (P1)

- **Finding:** `DESIGN.md` §15.1 defines today's layout as the floor canvas, a 360px right panel holding a terminal view and command bar, and a bottom strip of agent cards. Decision 17 moved terminals behind the advanced unlock, leaving that panel undefined, while five new surfaces needed homes: the attention strip, approvals inbox, connector center, office schedule and plain-language agent cards. Nothing said what an owner sees when they open the app at 9am.
- **Decision — read order on the owner's floor:**
  1. **Attention strip** across the top, shown only when something needs the owner (Decision 25).
  2. **Approvals inbox** in the 360px right panel, taking the slot the terminal view used to hold.
  3. **Floor canvas** in the centre, as the ambient view.
  4. **Agent cards** along the bottom, each describing its job in plain language.
- The **connector center** and **office schedule** live in Settings, not on the floor.
- **Morning-open state:** when anything needs the owner, the attention strip is the first thing they see; otherwise the floor, with overnight activity summarized on the agent cards.
- **`DESIGN.md` §15 gains an "owner floor" template** beside the existing one, carried by task T16.

**28. Setup has one progress counter, not two** (P2)

- **Finding:** the approved wireframe puts two different counters in the same title-bar slot: screen 1 reads "step 1 of 4" (wizard steps) and screen 3 reads "2 of 4" (agents to set up). Same position, same format, different meanings, and the second denominator moves with how many agents the owner picked.
- **Decision:** setup is a **single numbered sequence**, where each picked agent is its own step. The title bar reads "Step 4 of 7 · Set up Pam", and the step dots match that same total.
  - The total is computed once the team is picked, so choosing fewer agents visibly shortens setup.
  - Screens 1 and 2 show dots without a number, because the total isn't knowable yet.
  - One counter, one meaning, everywhere in the flow.

### Pass 2 — Interaction State Coverage (5/10)

**29. The first-run floor shows what happens next** (P1)

- **Finding:** setup ends and drops the owner onto the floor at the one moment when nothing has happened: no approvals, no activity, agents idle, attention strip empty by design. The plan specifies the busy floor in detail and never its first thirty seconds, which is exactly when an owner who just connected their inbox asks whether anything is actually working.
- **Decision — every empty surface names the next event rather than reporting absence:**
  - **Approvals panel, first run:** "Nothing needs you yet. Ryan drafts tomorrow's special at 9am."
  - **Agent cards:** each shows its first scheduled action with a time, so the floor reads as a promise with a timestamp.
  - **Other empty cases follow the same rule:** no agents picked, everything done for the day, office closed overnight. Each names the next event.
- **Requirement this creates:** every agent declares a first action at setup. A reactive agent such as Kelly states the trigger instead of a time ("Kelly replies when a catering enquiry arrives").

**30. A connection row names its state in words, not colour** (P1)

- **Finding:** after Decision 8 a connection has five conditions, and two of them look alike but behave differently: the Claude-account connection can read email but never send. `DESIGN.md` §17 requires status to be carried by colour **plus** icon **plus** position, never colour alone.
- **Failure scenario:** an owner sees green beside Email, assumes Kelly can reply, and a catering enquiry sits unanswered for two days.
- **Decision — five named states, each with a distinct pixel icon and plain words:**

  | State | Row reads |
  |---|---|
  | Read-only via the owner's Claude account | "Connected · reading only (through your Claude account)" |
  | Connected by the product | "Connected" |
  | Sign-in underway | "Signing in…" |
  | Token expired or revoked | "Needs reconnecting" |
  | Never connected | "Not connected" |

- The read-only row names its limit in the same place the owner sets what an agent may do.
- All five states are specified in `DESIGN.md` alongside the connector row component (task T16).
- **Check at the minimum window width (1280px)**, since the longer rows make the connector list taller.

**31. The approvals panel has two zones and eight specified states** (P1)

- **Finding:** an approval can be pending, queued behind another on the same connection (Decision 22), retrying, executed, failed, expired, rejected or superseded (Decision 10). An owner opening the app after the lunch rush sees a mixed list, and the difference between "this went out" and "this expired unsent" is the product.
- **Failure scenario:** an expired approval reads as a sent email, nobody re-approves it, and the customer who asked about catering never hears back.
- **Decision:**
  - The panel splits into **"Needs you"** (pending, queued, retrying) and **"Done today"** (executed, failed, expired, rejected, superseded), so position answers "what still needs me" before any word is read.
  - Each state carries its own icon, words and available action. A **failed or expired** item keeps an "Approve again" button. An **executed** item shows what went out and when.
  - Finished rows clear at the next office open.
  - All eight states are specified in `DESIGN.md` with the approvals row (task T16).
- **Density check required** at 1280×800: this is the tallest surface in the app and the 360px panel needs a scroll.

**Pass 2 re-rated: 9/10.** First-run, connection and approval states are now specified end to end. It falls short of 10 because loading states during sign-in and pack import are still unstated.

### Pass 3 — User Journey and Emotional Arc (4/10)

**32. The office announces its first success, and reports each morning** (P1)

- **Finding:** the arc runs anxious (handing over an inbox) → curious (a draft appears) → small risk (approving it) → and then the moment everything depends on, learning that it worked, which the plan never marks. Decision 10 writes the result to an agent inbox and a task card; Decision 31 adds a "Done today" row. Both are records, not moments.
- **Decision:**
  - **First success:** the first time an approval executes, the floor shows a one-time confirmation tying action to outcome — "Ryan posted your special. That's the first thing your office did for you." It fires once per install and never repeats.
  - **Morning report:** the first open of each day leads with what happened while the owner was away — "Overnight: Pam sorted 14 emails and flagged 2 for you" — so value is visible before any work is requested.
  - Both follow §14's voice rules: the agent's name, never "the agent", friendly and brief.

**Journey storyboard** (required artifact, rendered from the decisions above):

| Step | Owner does | Owner feels | Plan specifies |
|---|---|---|---|
| 1 | Installs, opens the app | Curious, slightly wary | Business type first; no folder, engine or model questions (Decision 16) |
| 2 | Picks business type | Recognized ("this is for me") | Six types, each a bundled pack; "Something Else" never dead-ends (Decision 3) |
| 3 | Reviews the suggested team | Interested, weighing | Michael always on, Oscar in every pack, needs-chips show setup cost (Decisions 2, 7) |
| 4 | Sets what each agent may do | Cautious, in control | Off / Ask me / On its own per capability; rules are editable defaults (Decision 4) |
| 5 | Connects an account | **Most anxious moment** | Issue 33 below |
| 6 | Lands on the floor | Expectant, unsure it works | Empty surfaces name the next event with a time (Decision 29) |
| 7 | Sees the first draft waiting | Curious, mildly protective | Approvals panel, "Needs you" zone (Decision 31) |
| 8 | Approves it | Small risk, hopeful | Broker executes the stored request exactly once (Decisions 10, 22) |
| 9 | Learns it worked | **Relief, first trust** | One-time first-success confirmation (this decision) |
| 10 | Opens the app next morning | Trust or doubt | Morning report of overnight work (this decision) |
| 11 | Week two, raises a level | Confident delegation | Levels are owner-editable at any time (Decision 9) |

Time horizons: the **first 5 seconds** are carried by step 2 (a screen about their business, not the software), the **first 5 minutes** by steps 3-6, and the **long relationship** by steps 9-11, where the office proves it works unattended.

**33. Permissions are set before the account is connected** (P1)

- **Finding:** the per-agent screen ordered itself connect → job → limits, so the owner granted access to the inbox their restaurant runs on before seeing what the agent could do with it. It also contradicted Decision 8, which requests a scope only when a capability sits above Off: at connect time the app does not yet know the levels, so it would have to request scopes it cannot justify.
- **Decision — the screen order becomes:**
  1. **What this agent does** (the editable does / won't rules).
  2. **What this agent may use** (the Off / Ask me / On its own levels).
  3. **Connect the account**, requesting exactly the scopes those levels need.
- The connect button carries a one-line summary of what is about to be granted: "Pam will be able to read and label your mail. She can't send unless you turn that on."
- **Consequence:** pack defaults must be good enough to review before connecting, and the approved wireframe's screen 3 changes shape.

**Pass 3 re-rated: 9/10.** The arc now has its anxious moment handled with informed consent, its payoff moment, and a recurring reason to return. It stops short of 10 because the storyboard's week-two step (raising a level after trust builds) has no designed prompt.

### Pass 4 — AI Slop Risk (6/10)

Classification: **APP UI (operate)**. App UI rules apply: calm surface hierarchy, dense but readable, utility language, cards only when the card is the interaction. **No hard-rejection criteria hit.** The outside voice agreed on the classification and found no hard rejections.

**34. Business-type tiles use pixel glyphs, not emoji** (P2)

- **Finding:** the first screen an owner ever sees used emoji as its only iconography (🍜 🛍 📋 ✂ 🔧 ?). `DESIGN.md` §14 states "Never: Emojis in copy. We have icons", §10 defines the pixel icon system, and "emoji as design elements" sits on the AI-slop blacklist. Emoji also render in each platform's own full-colour style, so a pixel-art cream interface receives glossy vendor artwork at whatever size the font picks, breaking both the ≤8-colour screen limit and the 4px grid.
- **Decision:** each business type gets a **16px two-colour pixel glyph** in the §10 style — bowl, shopfront, folder, scissors, wrench, question mark — snapped to the grid and drawn from the existing palette. The six glyphs are specified in `DESIGN.md` with the tile component (task T16).
- **Consequence:** every future Office Pack ships a glyph, so the pack schema gains an icon reference.

**35. The close dialog names each choice by its consequence** (P2)

- **Finding:** the three choices read "Minimize", "Close all agents gracefully" and "Force kill all". Graceful shutdown and force kill are process vocabulary; §14 sets the opposite register ("Ada hit a snag", never "An error has occurred"). This is also the one dialog where a wrong click destroys work in progress.
- **Decision — the three choices become:**
  - **"Keep the office running"** — minimize to the tray.
  - **"Send everyone home"** — finish current work, then quit.
  - **"Stop everything now"** — quit immediately; unfinished work is lost.
- The destructive choice sits last and uses the destructive button variant (§7.2). The same words carry into the tray menu, and the dialog is specified in `DESIGN.md` (task T16).
- **Translation note:** Chinese and Arabic wording must keep the consequence explicit, even where the office metaphor doesn't carry.

**Pass 4 re-rated: 9/10.** Classification is APP UI, no hard rejections, and the two slop-adjacent findings (platform emoji, process vocabulary) are resolved. Short of 10 because motion is still unspecified for the new components, which Pass 6 covers.

### Pass 5 — Design System Alignment (5/10)

**36. One readable floor at 14px, and `DESIGN.md`'s contradiction is resolved** (P1)

- **Finding:** §17 sets a hard floor — "never go below 14 px for any user-facing text" — while §4.1 defines `display-sm` at 8px for "Badges, chip labels", and the approved wireframe runs chips at 11px and secondary text at 12px. The system disagrees with itself and the new screens took the smaller side, on chips that carry meaning ("needs: Email", "starts in draft mode", "Connected · reading only") for an audience older than a developer tool's.
- **Decision:**

  - **§4.1 is amended:** `display-sm` is marked decorative-only and never used for load-bearing text, removing the conflict with §17 permanently (task T16).
  - **Density check at 1280×800**, since taller chips reflow the team-picker and connector rows.

**37. The thirteen new states reuse the existing status palette** (P2)

- **Finding:** §3.4 defines ten status colours and every one describes an agent's lifecycle. This review added two families the palette has never carried: five connection states (Decision 30) and eight approval outcomes (Decision 31). Without a mapping, the first surface built picks a green and the next picks a different one.

### Pass 6 — Responsive and Accessibility (3/10)

**38. The owner floor has a specified narrow layout, and approvals keep their slot** (P1)

- **Finding:** §15.1 sets a 1280×800 minimum and collapses the 360px right panel to a bottom drawer below 1024px. Decision 27 put the approvals inbox in that panel and Decision 31 made it the tallest surface in the app, so on a 13-inch laptop the thing owners open the app to check could become a drawer. Nothing stated what the attention strip, the taller 14px chips or the office-hours strip do as the window narrows.
- **Decision — behaviour by width:**
  - **At 1280px:** the right panel holds its 360px and the floor canvas absorbs the loss. The attention strip becomes a single line with a count. Chips wrap rather than truncate. The office-hours strip drops to two lines.
  - **Below 1024px:** the **floor canvas hides entirely** rather than the panel collapsing, so approvals survive the narrowest case.
  - This inverts §15.1's existing collapse for the owner layout, so the developer layout and the owner layout now collapse differently and both need checking.
- Written into `DESIGN.md` §15 alongside the owner-floor template (task T16). Gives the density checks from Decisions 30, 31 and 36 a defined target.

**39. Each new component states its keyboard contract, and the close dialog is safe by default** (P1)

- **Finding:** §17 promises Tab reachability with the §7.2 focus outline and reduced-motion support, but none of the eight new components said how. Two cases change outcomes rather than convenience: the three-way tool control would cost three Tab stops per capability (fifteen on Pam's screen alone), and nothing said which button the close dialog focuses or what Escape does, so Escape could land on the destructive choice.
- **Decision:**
  - **Tool level control** behaves as a radio group: one Tab stop per capability, arrow keys to change. Pam's five capabilities cost five Tab stops, not fifteen.
  - **Close dialog** opens with "Keep the office running" focused, and **Escape maps to that same safe choice**, never to "Stop everything now".
  - **Approval rows** are one Tab stop with their actions reachable from it; **attention-strip rows** are focusable; the **tray menu** follows OS conventions.
  - Focus order per screen and reduced-motion behaviour are specified in `DESIGN.md` with each component (task T16).

**Pass 6 re-rated: 9/10.** Narrow-width behaviour, keyboard semantics and destructive-dialog safety are now specified. Short of 10 until touch-target sizes are confirmed, which only matters if the office ever reaches a tablet.

## Folder & Knowledge Decisions

From the owner working through onboarding on 2026-09-22/23, after research into how the harness folder, per-agent workspaces and the Memory & Knowledge store are actually used. Each decision was made by the owner.

**What the research found**

- **Agents already use their hive workspace as a document store.** `hive/agents/<id>/` is defined in `PROTOCOL.md` as plumbing (`identity.md`, `memory.md`, `inbox/`, `outbox/`), but on the owner's install it holds 16 PDFs and spreadsheets in Oscar's workspace, 43 drafts in Ryan's and a 3,789-file project in Sadiq's. The hive root has also grown `shared/`, `templates/` and `social/` folders the agents made up. Nobody designed this. The workspace was the only place an agent was told was its own.
- **Those files are committed.** The hive is a git repo the app commits to automatically (11,147 commits, 90 MB `.git`), and it ignores only named plumbing files. 32 PDFs are now in its history.
- **Michael runs inside the harness folder.** `useHive.ts` spawns him with `cwd: config.harnessHome`, so everything he writes lands among the plumbing. Workers already run in a folder the owner picks, labelled "Project" in the hire modal.
- **The owner had already built the target design by hand:** workers pointed at `~/Documents/munder-difflin/moblizeit/{sales,support,marketing,hr,IT,finance,admin}`.
- **The app writes nothing into an agent's working folder.** Skills are copied into the agent's hive directory, and every other access to `cwd` is a read. Claude Code itself leaves one empty `.claude/.cc-writes/` directory there.
- **The harness folder cannot be synced.** It holds a git repo committed constantly, the Unix socket agents' permission hooks connect through (`hive/hooks.sock`, which fails open when unreachable), and a SQLite memory store (`palace/chroma.sqlite3`).
- **Memory & Knowledge could barely read an owner's files.** Word, Excel and PowerPoint were indexed as zip bytes and reported as a successful upload. PDFs needed a `pdftotext` binary a typical owner's Mac lacks. Images get no OCR. It is off by default, and when on, every agent is told to search it.

**44. Every agent works inside its own folder** (P1)

- An agent's folder is its **working directory**: the context it reads and the work it produces both live there, so drafts land in it without the agent having to remember.
- **Several agents can share a folder.**
- **Michael works in a shared "Office" folder**, which every agent can also reach. He leaves the harness folder.

**45. Folders default to `~/Documents/<Business name>/<Folder>`** (P1)

- The owner can instead point any folder at an existing location anywhere, including Dropbox or Google Drive. Documents may sync; only the harness folder must not.
- The app creates a default folder only if it is missing, and never overwrites an existing one.

**46. Agents can read and write their folders** (P2)

- Always read-write, by the owner's choice. An agent's edit or deletion in a synced folder syncs everywhere; the cloud providers' version history is the recovery path.

**47. Folders are suggested per agent during onboarding** (P1)

- Each pack names a folder for each agent (Oscar → Finance, Ryan → Marketing). On the pick-your-team screen the owner can accept it, point it elsewhere, or skip it.

**48. The harness folder is plumbing only: instruct and block** (P1)

- Agents are told where their work belongs, and the PreToolUse hook refuses writes into the harness folder outside plumbing paths.
- **Caveat:** that hook currently fails open when it cannot reach `hooks.sock`, so the block is not airtight until the fail-open is fixed. Writes made through a shell command cannot be blocked this way either.

**49. Existing files stay where they are** (P3)

- Business files already in the hive are neither moved nor purged from its history. The rules apply from now on.

**50. Memory & Knowledge is the company-wide store, and it reads real documents** (P1) — *built*

- It stays "what every agent should know", alongside per-agent folders.
- Word, Excel and PowerPoint are read from their XML (`fflate`), PDFs by a bundled PDF.js (`unpdf`), and `.doc`, `.rtf` and `.odt` through macOS's built-in `textutil`. Implemented in `src/main/docText.ts`, with 16 tests on real files.
- A file that cannot be read (a scan, Pages/Numbers/Keynote, a password-protected file) is **refused with a plain reason** that names the file, instead of being stored as junk and reported as added.
- **Scans and photos (F7):** read with the OCR built into macOS (the Vision framework behind Live Text, rendered page by page through PDFKit), reached via the built-in `osascript`. Nothing to bundle or download. First use loads Vision's models once (~30 s); a warm page takes under a second. Up to 50 pages per scan. On other platforms a scan is refused with a reason.

**51. Everything ships inside the DMG** (P1)

- No Homebrew, no system tools the owner must install. Verified by packaging the real `.app` and reading a Word file and a PDF through the libraries inside its `app.asar`, under the app's own Electron 32 / Node 20.

**52. Every character keeps the same job in every business type** (P1)

- The owner's rule: jobs follow The Office. Oscar is finance, Dwight sales, Kelly customer support, Pam executive admin, Ryan marketing, Sadiq IT security, Toby HR, Nick IT engineering, Creed quality control, Meredith supply chain, Darryl inventory and shipping. Michael is the office manager on every team.

- Nick, Sadiq and Darryl had no sprite. Each was added as a portrait recipe and rendered against the existing cast to check they read as distinct people.

**57. The app is "Don't Be Michael" and nothing points upstream** (P1)
